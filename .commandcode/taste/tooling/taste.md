# Tooling

- Uses dbt purely as a documentation tool — hand-typed docs rendered through the dbt docs feature — not as a modeling/transformation layer. Confidence: 0.9
- Expects pipeline outputs (e.g., data-quality results) to be persisted as queryable Iceberg tables that can be accessed directly from Superset via Trino for dashboard monitoring. Confidence: 0.6
- Prefers running pipeline work through the single high-level orchestration entry point (e.g., triggering the existing Airflow DAG `lake_to_warehouse`) over executing a chain of individual spark-submit scripts — when handed a multi-step manual runbook, asks whether the DAG can accomplish the same goal instead; expects the assistant to explain destructive side effects (e.g., a DAG rebuild wiping earlier point-in-time WAP inserts) before they run it. Confirmed by explicitly choosing to run the DAG first for a fresh silver+gold layer. Confidence: 0.6
- Follows a fixed warehouse run sequence in this project: refresh bronze→silver→gold via the orchestration DAG first, then re-apply point-in-time reconciliation (WAP dosen mapping), then run DQ checks — accepts that WAP inserts are lost whenever gold is rebuilt and must be re-run after each full refresh. Confidence: 0.5
- Wants the previously-standalone reconciliation flows (WAP skema/sdgs swap, WAP dosen mapping) and DQ checks wired into a scheduled Airflow DAG as a closed-loop "DQ audit → WAP fix → DQ re-audit" sequence — automation in the DAG, not manual spark-submit scripts, is the desired end state for these steps. Confidence: 0.8
- Prefers Airflow DAGs written in TaskFlow style using decorators (`@task.bash` decorated functions returning the shell command) over classic explicit `BashOperator` instantiation with `>>` chaining — when handed a DAG built from bare operators, explicitly asked to "change to taskflow rather than >>". Confidence: 0.75
